# Checklist Taxonomy Grouping — Implementation Plan

**Project:** ai-2d-checker
**Source:** Follow-on to `docs/hybrid-comparison-engine-implementation-plan.md` — reuses that plan's phase/completion-log conventions.

## Context

The checklist panel currently renders each of the 6 comparison categories (drawing_views, notes_section, bill_of_materials, title_block, isometric_view, other_engineering_references) as one flat list of individual findings. On a real drawing pair this gets cluttered — dozens of unrelated findings (a dimension change, a hole callout, a chamfer note) sit in one undifferentiated list under "Drawing Views" with no way to scan by topic. The user wants each category broken into a named sub-item taxonomy (e.g. Drawing Views → Origin, Dimensions, Hole Properties, Chamfer/Radius, ...) so the checklist reads as a scannable, organized inspection report.

Separately, the user flagged that in the title block, a checkmark can appear to "belong" to a static field-name label the same way it belongs to the field's actual value (e.g. "Unit No." reading as checked the same way its value "45" does). **Correction during planning:** the checkmark is a canvas-pin glyph drawn in `renderEntities.ts`/`DrawingCanvas.tsx` — placed at whatever CAD coordinates a marking resolves to — not anything rendered inside `ChecklistPanel.tsx`'s cards (which only ever show a colored status badge, never a checkmark glyph). So "checkmark only on the value" is a **coordinate-placement** concern: does a title-block/BOM finding's pin land at the value's position on the canvas, or the label's? It is not a request to redesign the checklist panel's card layout. Investigation during planning found this is already substantially handled by construction — `inject_title_block_markings` already searches for the *value* text's coordinates specifically, and `extract_title_ul_kv`'s own docstring already states "one marking per field, on the value row only" — so this plan's corresponding phase is a verification/hardening pass, not new UI work.

This requires one genuinely new concept in the data model: today `category` (one of 6 values) is the *only* grouping key anywhere — confirmed in both `ComparisonCandidate` and `CanvasMarking`. This plan adds a second, finer-grained `feature` key, tags it on both generators' output, and builds new two-level grouping UI to consume it. The existing per-finding card body in `ChecklistPanel.tsx` (badge + field name + ORIGINAL/REVISION values) is unchanged — only wrapped in a new feature-level accordion layer.

Two scope decisions were confirmed with the user before finalizing: (1) build real heuristic feature-classification for Generator A's free-form findings, not just Generator B; (2) always render every taxonomy sub-item, even empty ones, rather than only showing sub-items with findings.

## Architecture decisions

1. **`feature` is informational, never a reconciliation match criterion.** `reconciler.py::reconcile_candidates()` matches by category + 5mm proximity + status. This plan doesn't touch that — `feature` rides along on `ComparisonCandidate` like `entity_id` does today, decided independently by each generator before reconciliation runs.

2. **`canvas_markings` is the sole data source for the new grouped UI; `reference_content` is untouched.** Retrofitting a `feature` column into the existing markdown pipe-table string (parsed positionally by `ChecklistPanel.tsx::parseTabularContent()`) would duplicate a grouping mechanism the already-typed `canvas_markings` list can express natively. The new two-level UI reads `canvas_markings` exclusively; the existing flat-table path stays as a fallback (used today for `other_engineering_references`, which this plan gives no structured candidate source).

3. **Every category gets an implicit "Other / Unclassified" bucket, appended last** — for findings that don't match a taxonomy sub-item confidently. Never silently drop or force a false-confidence guess.

4. **Generator A's heuristic classifier is honest about where it has no signal.** Real regex/keyword signal exists for `chamfer_radius` (`C\d+`/`R\d+`), `geometric_tolerances` (GD&T frame chars + fit patterns like `+0/-0.1`), `hole_properties` (キリ/ザグリ/深サ/⌀), `welding_symbol` (△∨), `machining_symbol` (∇ — split out from where it's currently miscategorized under welding in the Gen B prompt), and `additional_views` (detail/section/arrow/詳細/断面/矢視 keywords). There is **no reliable text signal** for `origin`, `alignment_of_views`, `line_attributes`, or `text_attributes` — these default to `other` on the Gen A side; Generator B (which reasons visually) is the intended source for those four.

5. **Confirmed-both tie-break:** for `title_block`/`bill_of_materials`, always keep Generator A's `feature` (confident, structured lookup). For the other three categories, keep Generator A's only when it's not `other`/`None`; otherwise take Generator B's. Never blindly prefer one side.

6. **Named gaps — verified against the real extraction code, not assumed:**
   - **`line_name`** (title_block): no signal anywhere in `title_block_extractor.py`'s field list or label keywords. **Stub as always-N/A.** No extraction attempt.
   - **`revision_code`** (title_block, "if necessary"): `title_block_extractor.py`'s `label_keywords` list (line 73-81, confirmed) already recognizes `"amd."`, `"designchgno."`, `"訂正符号"` as label text — currently only used to *exclude* it from being mistaken for a value, never extracted as one. **Build real extraction** using the exact same `extract_proximity_value()` pattern every other field already uses. Do **not** reuse `revision_resolver.py::resolve_revisions()` — confirmed it hardcodes `ref_rev = "A"` / `rev_rev = "B"` as fallback defaults with no real match (lines 12, 22) and even forces them to differ via alphabet-increment when they'd otherwise collide (lines 32-37), which would fabricate a false CHANGED on every drawing pair with no real revision-code text at all.
   - **`numbering_arrangement`** (BOM, "assy"): the existing `NO` column covers "numbering." "Arrangement" (visual row ordering) has no signal — map only the numbering half.
   - **`ballooning`** (BOM): confirmed real, working code already exists — `row_extractor.py::detect_balloons()` (circle+numeric-text detection) / `reconcile()` (BOM cross-check) — but it's wired into the separate standards-compliance audit path, never into the physical-comparison candidate pipeline. **Build the integration** (real new logic, not a label change).

7. **Canvas-pin value-only placement is a verification/hardening pass, not new UI.** Confirmed both generators are already designed to resolve title-block/BOM coordinates to the value, not the label (see Context). This plan's corresponding phase (7) audits the actual coordinate-resolution code paths for any fallback that could leak a label's position, and adds one lightweight safety net: cross-check a resolved title-block/BOM coordinate against known label-text positions (the same `label_keywords`/`field_labels_map` data already used elsewhere) and null the coordinate out — forcing it through the existing fallback chain — rather than ever pinning a checkmark on a label.

## Canonical taxonomy

New file `services/backend/infrastructure/audit/comparison/taxonomy.py`, hand-mirrored at `apps/desktop/src/utils/comparisonTaxonomy.ts` (no runtime type-sharing exists between the two languages in this repo — same precedent as `comparisonStages.ts`). Add a comment in each file pointing at the other by path.

```
drawing_views: origin, alignment_of_views, line_attributes, dimensions, hole_properties,
  chamfer_radius, machining_symbol, welding_symbol, geometric_tolerances,
  additional_views, text_attributes
notes_section: standard_notes, special_notes
bill_of_materials: material_type, material_specification, quantity, material_weight,
  ballooning, remarks, numbering_arrangement
title_block: machine_name, line_name, scale, designed, drawn, quantity, job_number,
  cross_reference_number, previous_drawing_number, revision_code
isometric_view: orientation, scale, location
other_engineering_references: tree_view_properties, excel_additional_info
```

Plus `OTHER_FEATURE_KEY = "other"` (appended by grouping code, not part of the arrays), `DEFERRED_FEATURES = {"line_name"}` (frontend renders a muted "not yet supported" state instead of a normal empty state), and `normalize_feature(category, raw) -> str` (NFKC/lowercase/whitespace-normalized match against known keys/labels, falls back to `other`). Each entry carries both a stable snake_case `key` (used as the `feature` field value) and a display `label` — the taxonomy is the single source of truth for display labels, so individual markings do not need their own label field.

## Build order

1. **Phase 1** — Schema field (`feature`) + taxonomy module. No behavior change.
2. **Phase 2** — Generator A tagging: structured 1:1 lookups (title block + BOM), heuristic classifier for free-form findings, title-UL feature classification, ballooning integration, revision_code extraction.
3. **Phase 3** — Generator B prompt/schema changes (shared by `rag_ai`/`ai_vision`/hybrid Gen B).
4. **Phase 4** — Hybrid reconciliation: confirmed-both feature tie-break.
5. **Phase 5** — Frontend taxonomy constant + threading `feature` through `markerGenerator.ts`/`roomStore.ts`.
6. **Phase 6** — `ChecklistPanel.tsx`: two-level (category → feature) grouping UI, always-render-empty-sub-items. Existing per-finding card body is unchanged.
7. **Phase 7** — Canvas-pin value-only coordinate placement: audit + lightweight safety net.
8. **Phase 8** — Testing & verification.

Phases 1→2→(3,4) chain on the backend (2 and 3 can run in parallel once 1 lands; 4 needs both). Phase 5 only needs Phase 1's field shape, can start in parallel with 2/3/4. Phase 6 needs Phase 5. Phase 7 is independent of 1-6 (it's a coordinate-resolution audit, not a taxonomy feature) and can run any time, though doing it after Phase 2/3 makes sense since those phases touch the same marking-injection code paths. Phase 8 depends on everything.

## Out of scope

- Real extraction for `line_name` (no signal exists) — stubbed always-N/A.
- BOM "arrangement" detection (only "numbering" is covered).
- Retrofitting full TypeScript types for `CategoryComparison`/`CanvasMarking`/`PhysicalComparisonResponse` in `packages/types` — confirmed that package has an unrelated legacy model; the frontend treats this payload as `any` throughout today, and fixing that broadly is a separate effort. Only the new taxonomy constant is fully typed.
- Any redesign of `ChecklistPanel.tsx`'s existing per-finding card body (badge + field name + ORIGINAL/REVISION grid) — confirmed out of scope after the checkmark-placement correction; only a new grouping wrapper is added around it.
- Per-feature `ComparisonDiagnostics` counters (only per-category exists today) — plausible fast-follow, not required here.
- Extending `UNIT NO`/`PART NO`/`STOCK QTY` title-block fields (extracted today but never surfaced as markings) — pre-existing gap, not this plan's job.
- Retuning the reconciler's 5mm match radius or any existing hybrid-pipeline constant.
- A standalone "browse by feature across categories" view — grouping stays nested inside each category's existing card.
