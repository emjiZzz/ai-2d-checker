## 1. Architecture decision for Phase A (read before starting that phase)

**The fix is not "encrypt session tokens with a better key" — it's "sign them with a secret only the server has."**

Current flow: client sends username/password → server encrypts a JSON payload with a key derivable from public env vars → client presents the encrypted blob as proof of identity on every request. The payload's confidentiality (AES-GCM) was never the property that mattered here — what's missing is **authenticity**: proof the payload was issued by the server and not fabricated by whoever's sitting at the keyboard.

**Decision:** switch `core/auth.py` from AES-GCM encryption to HMAC-SHA256 signing, using the exact same secret-generation/persistence pattern `core/security.py::initialize_local_api_token()` already uses correctly for the API bearer token — `secrets.token_hex(32)`, persisted encrypted-at-rest via the existing `AES256GCM` class (which is fine for *storage*, just not for *deriving a key from public info*), loaded once at startup.

**Why not just fix `_derive_device_key()` to use a random value instead of env vars?** Because `AES256GCM.encrypt()` provides confidentiality, and a session token doesn't need to be secret from the person holding it — it needs to be *unforgeable*. Encryption without a MAC of the plaintext claims is the wrong primitive for "prove this claim came from the server." HMAC (or keeping AES-GCM but treating the GCM auth tag as the actual security property — a valid GCM tag still requires the key, which is the same requirement) both work; HMAC is simpler to reason about here and matches how `jti`/`exp` claims are conventionally protected. Don't reach for a JWT library — the existing `create_jwt_token`/`verify_jwt_token` shape (dict payload, `exp`, `jti`) is fine, only the "how is this thing tamper-proof" mechanism changes.

**New session-secret storage:** don't reuse `settings.API_TOKEN` for this — that token already has a distinct purpose (machine-level Bearer auth, checked before any user-level auth even runs) and mixing the two collapses two independent trust boundaries into one secret. Add a second persisted secret, `SESSION_SIGNING_KEY`, generated and stored the same way (`storage/secure/.session-key`, encrypted at rest with the existing `AES256GCM` — using it for storage-at-rest here is fine, since the key protects a value that's read back into memory then compared, not derived from guessable inputs).

**What does NOT change:**
- `get_current_user`'s DB-backed role lookup (`api/dependencies.py`) — that logic was already correct, it just currently trusts a forgeable input.
- The `X-Session-Token` header name/mechanism, request flow, or frontend `authStore.ts`/`fetchUtils.ts` — the token is still an opaque string in a header; only what's inside it and how it's validated changes. Frontend code should need zero changes.
- `core/security.py::verify_api_token` (Bearer token layer) — that's already sound, untouched.

1. **Phase A** — `core/auth.py` + `core/encryption.py` + `core/security.py`: replace device-derived AES key with a persisted random HMAC secret; switch `create_jwt_token`/`verify_jwt_token` to sign-and-verify instead of encrypt-and-decrypt. 4. **Phase D** — `infrastructure/audit/comparison/spatial_differ.py`: constrain the widened second-pass match radius; fix `calculate_global_offset`'s first-match-wins behavior for duplicate-text entities.

### Phase A — Session token signing (finding #1)

- Generate `SESSION_SIGNING_KEY` the same way `initialize_local_api_token()` generates `API_TOKEN`: `secrets.token_hex(32)` on first run, persisted encrypted at `storage/secure/.session-key` via the existing `AES256GCM` class, loaded on subsequent starts. Don't derive it from anything guessable — this is the one spot in the file where "device-bound" reasoning is explicitly the wrong pattern.
- `create_jwt_token`: build the payload (`username`, `exp`, `jti`, whatever else is currently included) as JSON, compute `hmac.new(session_key, payload_bytes, hashlib.sha256).hexdigest()`, return `base64(payload) + "." + signature` (or any deterministic two-part format — just document whatever's chosen). Use `hmac.compare_digest` for verification, never `==`.
- `verify_jwt_token`: split on the delimiter, recompute the HMAC over the decoded payload, `hmac.compare_digest` against the provided signature before trusting anything in the payload (including `exp`) — check the signature first, then expiry, not the other way around.
- **This invalidates every existing session on deploy** (old tokens were encrypted, new verification expects signed) — that's correct and expected, not a regression to work around. Don't add a "try old format, fall back to new" compatibility shim; this app doesn't need backward-compat sessions and adding one just reintroduces a code path where a forged old-format token might still work.
- Rename `create_jwt_token` → `create_session_token`, `verify_jwt_token` → `verify_session_token` while this file is open (finding #7). Update the one call site in `api/dependencies.py::get_current_user`. Grep for any other references before finishing — don't assume `dependencies.py` is the only caller.
- Update `LoginResponse.session_token`'s docstring in `api/schemas.py` (`"AES-256 encrypted active session identifier"` → reflect the new signed format) — small, but a stale docstring here is exactly the kind of thing that misleads the next person reading this file.
- Leave `AES256GCM`/`encryption.py` itself alone otherwise — it's still correctly used for at-rest storage (the API token file, and now the session-signing-key file). Only `core/auth.py`'s *use* of a device-derived key for token authenticity is wrong; the class itself isn't the problem.

### Phase D — Spatial matching false-positive risk (finding #4)

- `match_pass`'s widened second call: `widened_threshold = max(150.0, distance_threshold * 5.0)` — constrain this so it can't match across unrelated regions of a drawing. Two reasonable options, pick one and document the choice: (a) cap the widened threshold at a fixed absolute ceiling regardless of the multiplier (e.g. never exceed ~300 units even in fuzzy mode), or (b) require same-text matches only in the widened pass (drop the `dist + 1000.0` fallback for the second pass specifically, so it only rescues same-text pairs that got missed on the first pass due to jitter, not new cross-text guesses at long range). Option (b) is closer to the actual intent ("catch large-distance structural edits" per the existing comment) — a long-range match between *different* text was never a structural edit, it's a false pair.
- `calculate_global_offset`: the `break # Just take the first one for offset estimation` — change to pick the *nearest* ref coordinate when a normalized text has multiple ref entities, not the first in list order. This only affects offset estimation (median-smoothed already), so it's a correctness improvement, not a critical fix — don't over-invest time here relative to the match_pass change above.
- After the fix, re-run whatever test/sample drawings exist under `tests/` or `services/backend/` (check what's actually runnable — the audit didn't verify test infra) against a drawing known to have repeated dimension labels, and confirm no new false MATCHED/CHANGED pairs appear that weren't there before, and no previously-correct matches got dropped by the tightened threshold.
