# Hybrid Comparison Engine — Implementation Plan

**Project:** ai-2d-checker
**Source:** "Comparison Engine — System Teardown" session (2026-07-23) — reverse-engineered `rag` / `rag_ai` / `ai_vision`, then revised the proposed unified method to a two-generator + narrow-verifier design based on the specific failure mode identified in that conversation: the deterministic `SpatialDiffer` can itself mis-pair entities and flag a false CHANGED, and today's guardrail only ever trusts it, never checks it.
**Scope:** Add a fourth comparison method, `comparison_method="hybrid"`, that runs the existing deterministic diff and the existing AI Vision scan as two independent generators, reconciles their findings by location, and resolves disagreements with a narrow, bounded, crop-based verifier — instead of the current one-directional override. **Additive.** `rag`, `rag_ai`, and `ai_vision` are not removed, deprecated, or changed in observable behavior by this plan.
**Estimated effort:** ~6–9 dev days across 9 phases. Phase 2 (candidate refactor) and Phase 3 (reconciliation + verifier) are the real engineering; everything else is comparatively mechanical wiring, but shouldn't be skipped because it's small — Phase 6 (frontend) and Phase 8 (telemetry) are what make the other work visible/useful instead of a backend feature nobody can see or measure.

---

## 0. What this plan builds

Today, `rag_ai`/`ai_vision` hand Gemini a comparison task and, after the fact, silently overwrite Gemini's BOM/title-block verdict with the deterministic one if they conflict (`full_ai_orchestrator.py:349–405`). That assumes the deterministic side is always right. It usually is, but `SpatialDiffer` pairs reference↔revision entities by nearest position + text value — a shifted entity, a re-numbered label, or a drifted zone bbox can make it confidently flag a difference that isn't real, and nothing today catches that direction of error.

The fix isn't a smarter override rule — it's not trusting either side by default. `hybrid` runs:

1. **Generator A** — the existing deterministic diff, unchanged, reframed as producing *candidates* instead of a final verdict.
2. **Generator B** — the existing AI Vision scan, unchanged, also reframed as producing *candidates*, run independently — it never sees Generator A's output, so it can't inherit its mistakes.
3. **Reconciliation** — match the two candidate lists by location. Agreement is trusted directly. Disagreement (or a finding only one side produced) goes to step 4.
4. **Crop verifier** — a narrow, bounded, batched Gemini call (same shape as the existing title-block OCR call, not the open-ended comparison call) that looks at just the disputed location on both drawings and resolves it to confirm-A, confirm-B, or **CONFLICT** — a new terminal state that gets flagged for human review instead of silently resolved either way.

## 1. Architecture decisions (read before starting any phase)

### 1.1 Candidates, not verdicts
Both existing generator functions currently build `CanvasMarking` entries directly into a `PhysicalComparisonResponse`. For `hybrid`, both need to stop at an intermediate, unpersisted shape — a `ComparisonCandidate` — that reconciliation and the verifier can operate on *before* anything is final. This is a refactor of `orchestrator.py` and `full_ai_orchestrator.py`'s internals, not a rewrite: the actual diffing logic (`SpatialDiffer`, the Gemini `ai_vision` prompt) does not change. `rag`, `rag_ai`, and `ai_vision` keep calling the same functions today, which become thin wrappers around the new candidate-producing internals — their output must be byte-for-byte unchanged after this refactor (see Phase 2 verification).

### 1.2 Coordinate resolution runs twice, not once — the diagram simplifies this
The teardown diagram shows one "Coordinate resolution" box after the verifier. In practice, reconciliation *needs* coordinates to know two candidates are "the same location" — so each generator's candidates must get at least entity-handle/visual-bbox resolution **immediately after generation**, before reconciliation, exactly as `rag_ai`/`ai_vision` already do internally today (`resolve_marking_coordinates`, then the visual-bbox fallback in `full_ai_orchestrator.py:484–521`). What actually happens once, at the end, is DTO-level *normalization* — the `Coordinate2D`/`BoundingBox2D` validation pass and the CAD↔visual bbox cross-mapping both orchestrators already do as their last step before returning. Build it as: **per-generator resolve → reconcile → verify → final normalize**, not four sequential black boxes.

### 1.3 Reconciliation is fuzzy spatial matching, not exact-key matching
Generator A's coordinates come from exact entity handles; Generator B's come from the same handle lookup where text matched, or the visual-bbox estimate otherwise — so "the same finding" from both sides won't have identical coordinates. Reuse the existing 5 mm CAD-distance dedup threshold (`full_ai_orchestrator.py:562–585`) as the match radius, plus require `category` to match and `status` to be compatible (MATCHED only matches MATCHED; CHANGED/ADDED/REMOVED are compared as "did both sides flag *something* here" before comparing which specific status). A det candidate with no AI candidate within radius, or vice versa, is a **single-source** case — treated the same as a disagreement (goes to the verifier), not auto-trusted, since "only one generator saw this" is exactly the coverage-gap case Generator B exists to catch and the entity-mispairing case Generator A is prone to.

### 1.4 The crop verifier reuses the OCR call shape, not the comparison call shape
`execute_gemini_cascade` (the open-ended, whole-drawing, Pro→Flash→Fallback call) is the wrong shape for verification — it's what already produces the boxed-in, occasionally-wrong judgments this plan exists to check. The verifier should look like `execute_title_block_ocr`: Flash-tier only, `response_schema`-constrained, one batched call covering multiple disputed findings' image crops at once, asked a narrow yes/no-with-reasoning question about a specific location — not "compare these drawings."

### 1.5 The BOM/title override hack goes away — reconciliation replaces it
Today's hardcoded post-hoc override for exactly two categories (`full_ai_orchestrator.py:349–405`) exists because there was no general mechanism for "the deterministic side disagrees with the AI side, now what." Under `hybrid`, BOM and title-block extraction still runs as part of Generator A like today, but it's no longer special-cased — it's just two categories where Generator B will rarely disagree, going through the same reconciliation path as everything else. **Delete the two hardcoded override blocks when building `hybrid`'s orchestrator; do not port them over.** (They stay in `full_ai_orchestrator.py` untouched, since `rag_ai`/`ai_vision` still need them.)

### 1.6 New method, additive
Add `"hybrid"` to the `comparison_method` literal everywhere it's declared (`api/schemas.py:176,186,202`, `domain/models/room.py` — confirm its field type before editing, not yet inspected this session — and the frontend union types listed in Phase 6). Dispatch it in `api/routers/audits.py::perform_physical_comparison` (~line 480) as a third branch alongside the existing `if method in ("rag_ai","ai_vision")` / `else`. New orchestrator file: `infrastructure/audit/comparison/hybrid_orchestrator.py::perform_hybrid_comparison(...)`.

### 1.7 CONFLICT is a real, visible state — not resolved silently
A finding the verifier can't confirm either way must reach the frontend as `status="CONFLICT"` with `verification="conflict"`, not get coerced into MATCHED or CHANGED. This is the one truly new user-facing concept this plan introduces — see Phase 6. Shipping the backend without this would recreate exactly the "silently pick a winner" problem this design exists to fix.

## 2. Build order

1. **Phase 1** — Data model: extend schemas with `CONFLICT` status, candidate provenance fields, method literal, diagnostics counters. No behavior change.
2. **Phase 2** — Refactor `orchestrator.py` and `full_ai_orchestrator.py` internals to produce `ComparisonCandidate` lists. Existing 3 methods must be behavior-identical after this phase.
3. **Phase 3** — New reconciliation module + new crop verifier module (generalizes `crop_title_block_image`, adds `execute_crop_verification`).
4. **Phase 4** — `hybrid_orchestrator.py` wiring the above into one pipeline; router dispatch.
5. **Phase 5** — Provenance-aware confidence scoring per finding.
6. **Phase 6** — Frontend: 4th toggle option, CONFLICT rendering, verification-state indicator.
7. **Phase 7** — Caching: separate generator-output cache from reconciliation/verification cache.
8. **Phase 8** — Telemetry: per-category agreement/conflict counters (measurement only — no auto-gating logic).
9. **Phase 9** — Testing & regression verification.

Phases 1→2→3→4 are a strict dependency chain. Phases 5, 7, and 8 can proceed in parallel once Phase 4 exists (they touch different files: confidence scoring, cache_manager, diagnostics logging). Phase 6 can start once Phase 1's schema is settled — the frontend types don't need Phase 4 to be done, just the field shapes. Phase 9 depends on everything.

## 3. Explicitly out of scope for this plan

- **Removing or changing `rag`, `rag_ai`, or `ai_vision`.** They stay as-is, including the BOM/title override hack inside `full_ai_orchestrator.py` (section 1.5 only removes it from the *new* `hybrid` path).
- **Auto-gating Generator B off for low-conflict categories.** Phase 8 builds the counters this would need; the gating logic itself is a follow-up plan once real per-category agreement data exists (this is the explicit tradeoff named in the teardown's cost/benefit section).
- **Fixing `LocalEmbeddingModel`** (the hash-based fake embedding on the *separate* standards-compliance audit RAG path). Unrelated subsystem, its own finding, its own plan.
- **A dedicated "review conflicts" screen.** Phase 6 makes CONFLICT visible through the existing checklist/canvas-marking UI (new status color + a verification-state badge); a standalone triage workflow for reviewers is a plausible fast-follow, not required to ship this.
- **Tuning the crop margin, batch size, or confidence constants to their final values.** Phase 3 and Phase 5 ship with stated placeholder numbers; tuning against real drawings happens after Phase 9's manual QA, as its own short pass.
- **Making Generator A and Generator B run concurrently as a performance optimization beyond the straightforward `asyncio.gather`** named in Phase 4 — deeper latency work (streaming, speculative caching) is out of scope here.

### Phase 3 — Reconciliation + crop verifier
*The core new logic.*

- New file `infrastructure/audit/comparison/reconciler.py`:
  - `reconcile_candidates(det: list[ComparisonCandidate], ai: list[ComparisonCandidate]) -> ReconciliationResult` where `ReconciliationResult` holds three buckets: `confirmed` (candidate pairs within 5 mm, same category, compatible status — pick det's coordinates since they're exact, keep both text_contents for the verifier/audit trail even when not disputed), `disputed` (mismatched status at the same location, or a candidate with no counterpart within radius on either side).
  - Matching detail: iterate det candidates, find nearest ai candidate within radius+category (greedy nearest-neighbor is fine here, same tolerance for false-pairing risk as `SpatialDiffer` already accepts elsewhere in this codebase); unmatched candidates from either list are disputed by definition.
- `infrastructure/rendering/image_cropper.py`: generalize `crop_title_block_image(drawing_id, metadata, entities)` → new `crop_region_image(drawing_id, metadata, cad_bbox: tuple[float,float,float,float], margin_pct: float = 0.15) -> Optional[bytes]`, parameterizing the bbox instead of calling `compute_title_block_bbox` internally, and padding the crop by `margin_pct` of the bbox's width/height so minor coordinate jitter between the two generators doesn't crop the disputed content out of frame. Reimplement `crop_title_block_image` as a one-line wrapper calling `crop_region_image` with the title-block bbox — zero change for existing OCR call sites.
- New file `infrastructure/audit/comparison/crop_verifier.py`:
  - `execute_crop_verification(api_key, disputed: list[DisputedFinding]) -> dict` — same shape as `execute_title_block_ocr`: build a `DynamicResponse` via `pydantic.create_model` keyed by a finding id, schema per finding = `{differs: bool, confirms: Literal["A","B","neither"], reasoning: str}`. Contents: for each disputed finding, the ref crop + rev crop (via `crop_region_image` on each drawing's own render) labeled with the finding id, then one system instruction explaining the task once for the whole batch (not per-finding).
  - **Batch size:** cap at 8 disputed findings per call (chunk larger disputes into multiple calls) — this number is a placeholder based on reasonable multipart-payload size, not derived from measurement; **flag for tuning in Phase 9** once real payload sizes are observed.
  - `Flash-tier only`, matching `execute_title_block_ocr`'s reasoning (bounded extraction/verification task, not open-ended).
  - Resolution mapping: verifier `confirms: "A"` → det candidate wins, `verification="confirmed_single"`, `origin="deterministic"`; `confirms: "B"` → ai candidate wins, same verification value, `origin="ai_vision"`; `confirms: "neither"` or the two crop-verifier calls in different chunks contradict each other → `status="CONFLICT"`, `verification="conflict"`.

### Phase 4 — `hybrid_orchestrator.py` + router wiring

- New file `infrastructure/audit/comparison/hybrid_orchestrator.py::perform_hybrid_comparison(request, ref_drawing, rev_drawing, ref_entities, rev_entities) -> PhysicalComparisonResponse`:
  1. Cache check first (Phase 7's cache scheme) — if a full hybrid result is cached, return it, skip everything below.
  2. `asyncio.gather(generate_deterministic_candidates(...), generate_ai_vision_candidates(...))` — these are independent (Generator A makes no LLM call, Generator B makes one), so running them concurrently is a straightforward latency win over the sequential pattern the other methods use; call this out as it's a small but real deviation from how `rag_ai`/`ai_vision` are structured today.
  3. Per-generator coordinate resolution (section 1.2) — reuse `resolve_marking_coordinates` + the visual-bbox fallback, applied to each candidate list independently before reconciliation.
  4. `reconcile_candidates(...)` (Phase 3).
  5. For the `disputed` bucket: `execute_crop_verification(...)` (Phase 3), chunked per the batch-size cap.
  6. Merge `confirmed` + resolved-`disputed` into one final candidate list; anything still `CONFLICT` stays in with that status.
  7. Final coordinate DTO normalization pass (the `Coordinate2D`/`BoundingBox2D` validation block both existing orchestrators already do at the end — reuse verbatim).
  8. Confidence scoring (Phase 5).
  9. Convert candidates → `CanvasMarking`/category `CategoryComparison` dicts, build `PhysicalComparisonResponse` with `ComparisonDiagnostics` populated from Phase 8's counters.
  10. Persist `AuditSession` + `AuditViolation`s (mirror the pattern in both existing orchestrators; `source="hybrid_comparison"`), cache, return.
